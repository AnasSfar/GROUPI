- **Ch.14 — Présences** : saisie progressive par le Professeur (`PUT /sessions/:id/attendance/:studentId`), un statut unique par élève (Présent/Retard/Absent excusé/Absent non excusé), retard borné à la durée de la séance (ERR-ATT-016/017/022). `NON_RENSEIGNEE` n'est jamais persisté (ligne absente = non renseigné) ; réinitialisation possible tant que la séance n'est pas validée (`DELETE`). Validation définitive (`POST .../validate`) exige un statut pour chaque inscription active du groupe et fait passer la séance `PLANNED → COMPLETED` — la transition `COMPLETED → LOCKED` à l'expiration des 48h (`computeLockDeadline`/`isLockable`, réutilisés depuis `sessions.service.ts`) est appliquée paresseusement à la lecture, comme l'expiration des `Enrollment`. `VERROUILLEE` n'est pas non plus une valeur stockée : le verrouillage se déduit de `Session.status`, ce qui évite de perdre le statut réel au moment du verrouillage. Historique complet des corrections (`AttendanceHistory`, jamais supprimé). Détection d'abandon (absences non excusées consécutives vs `Group.abandonmentThreshold`), statistiques d'assiduité par élève sur 3 périodes, registre de présence du groupe. Écrans `/teacher/sessions/:id/attendance` (saisie/validation, alerte d'abandon), `/teacher/groups/:id/attendance` (stats + registre), `/parent/children/:id/attendance` (lecture seule).   - **Compte de suivi comptable** : un par inscription (`AccountingAccount`, 1-1 avec `Enrollment`), créé automatiquement — état initial `CREATED` — à l'activation (`EnrollmentsService.accept`, et `GroupChangeService.accept` pour la variante définitive du changement de groupe, Ch.12.12), passe `ACTIVE` dès la première écriture.   - **Écritures** (`AccountingEntry`) : PAYMENT/SESSION/ADJUSTMENT/ADMIN_ADJUSTMENT, numérotées séquentiellement `ECR-<année>-000001` (compteur atomique Postgres par année civile), montant toujours positif avec un champ `direction` CREDIT/DEBIT distinct du type (une correction de paiement reste de type PAYMENT mais peut être un débit — RM-CPT-008 "type immuable"). Solde et tous les indicateurs sont **recalculés à la demande**, jamais stockés (RM-CPT-031), à partir des écritures non-brouillon (POSTED/LOCKED/REVERSED — une écriture REVERSED reste comptée, neutralisée par sa propre écriture inverse, pas par exclusion : les deux mécanismes cumulés auraient annulé l'opération deux fois, bug détecté et corrigé pendant les tests e2e).
  - **Immutabilité** (RM-CPT-005/017/028/029) : aucune écriture n'est jamais modifiée ni supprimée ; corriger ou annuler un paiement crée toujours une écriture inverse (+ une nouvelle écriture correcte pour la correction), l'originale passant `REVERSED`. Écritures SESSION générées automatiquement à la validation définitive des présences (hook dans `AttendanceService.validate`, une par présence facturable selon `absenceBillingPolicy` — réutilise `isBillable` déjà existant), un ajustement Professeur n'est possible que dans la fenêtre de 48h suivant la séance (réutilise `computeLockDeadline`/`isLockable` de `sessions.service.ts`, ERR-CPT-004) ; passé ce délai ou sur un compte verrouillé, seul un ajustement administratif (`ADMIN_ADJUSTMENT`, permission `CPT_ADMIN_ADJUST`) reste possible.
  - **Indicateurs financiers** (Ch.15.12, ~30 indicateurs) : compte (solde, payé/facturé/restant, moyennes, historique du solde, jours créditeur/débiteur, plus forte avance/dette, ancienneté de la dette, ajustements, remises, rappels envoyés...), Professeur et Groupe (CA prévisionnel/réalisé/encaissé/à recevoir, comptes débiteurs/créditeurs, taux d'encaissement/impayés, encours, meilleur/pire mois...) — tous recalculés à la demande. Quelques heuristiques documentées faute de spécification exacte dans le référentiel : délai moyen d'encaissement (appariement chronologique séance↔paiement suivant, pas un lettrage comptable réel), taux de régularisation des dettes (comptes ayant déjà été débiteurs et aujourd'hui régularisés). Doublons littéraux du référentiel (ex. NOT-CPT-006/010, "nombre de comptes en alerte"/"en risque élevé") volontairement dédupliqués plutôt que recalculés deux fois pour la même définition.

    - **Correctif (repéré via des données de démonstration manuelles, pas par les tests automatisés initiaux)** : le franchissement de seuil comparait les deux dernières lignes du relevé de solde recalculé. Comme une écriture SESSION est toujours datée de la séance facturée (`effectiveDate`), valider une séance ancienne *après* avoir déjà encaissé un paiement du jour insère cette écriture **avant** le paiement une fois le relevé trié par date d'effet — la comparaison "queue du tableau" pouvait alors comparer deux soldes n'ayant jamais réellement fait suite l'un à l'autre, déclenchant une fausse alerte en double.   - **Administrateur / Super Administrateur** (`GET /dashboard/admin`/`/dashboard/super-admin`, RM-DSH-007/16.5/16.6) : tout Admin/Super Admin peut atteindre son tableau de bord (`RolesGuard`, `PERM-DSH-002`) — le contenu, lui, dépend entièrement des permissions détenues (`ERR-DSH-002` traité comme *masquage section par section*, pas comme un refus global de la route) : comptes en attente de validation (`ACC_VALIDATE`), situations scolaires en attente (`SCH_VALIDATE`), abonnements (`ABO_VALIDATE`), journal d'audit (`AUDIT_VIEW`, **nouvelle permission mintée pour ce chantier** — aucun endpoint de lecture des `AuditLog` n'existait avant Ch.16, écrit seul jusqu'ici). Vue d'ensemble (comptes/groupes/élèves/inscriptions actifs) et référentiels toujours visibles (mêmes données que les endpoints publics existants). Le Super Admin voit tout sans filtrage (`getSuperAdminDashboard`, `totalAdminsCount` en plus).
  - **RM-DSH-008** (Super Admin, lecture seule du tableau de bord d'un autre utilisateur) : `GET /dashboard/users/:userId`, réservé au rôle `SUPER_ADMIN`, aiguille vers le bon tableau (Professeur/Parent/Admin avec ses propres permissions réelles) ; consulter le tableau de bord d'un Super Admin est explicitement refusé, même pour un autre Super Admin. Endpoint backend uniquement — pas d'écran d'impersonation dédié côté frontend (voir "Hors scope").
  - **Écrans** : `/dashboard` entièrement réécrit — widgets riches par rôle (Activité/Présences/Comptabilité/Paiements/Groupes/Profil/Statistiques/Préinscriptions pour le Professeur, carte par enfant pour le Parent avec bouton "Signaler une absence" inline, vue d'ensemble/référentiels/sections conditionnelles pour l'Admin/Super Admin) au-dessus de la grille de liens rapides existante (conservée, renommée "Accès rapide"). Nouveau composant `AlertList` réutilisé par les trois rôles.
  - **Tests** : 19 tests e2e dédiés (agrégation Professeur avec occupation/abandon/compte débiteur/alertes croisées, gating Statistiques/Export par abonnement, préinscriptions, alerte d'échéance d'abonnement, vue Parent consolidée avec solde global, signalement d'absence + notification immédiate + refus hors délai (ERR-DSH-007) + refus pour un tiers, masquage des sections Admin par permission, Super Admin sans filtrage, RM-DSH-008 dans les deux sens (consultation autorisée / tableau de bord Super Admin protégé) + RolesGuard sur toutes les routes).

## Repères pratiques

- `dev.bat` à la racine lance Postgres (Docker) + API (port 3000) + Web (Vite, port 5173/5174).
- `npm run bootstrap:admin --workspace apps/api` crée le Super Admin de dev (idempotent, voir `.env` pour les identifiants).
- Migrations Prisma : `npx prisma migrate dev --name <nom>` depuis `apps/api`.
- **Convention locale : tous les mots de passe des comptes de test/dev sont `admin-local`** (`admin@groupi.local`, `prof1@test.com`, `parent1@test.com`). Nouveaux comptes de test à créer avec ce mot de passe pour rester cohérent.
